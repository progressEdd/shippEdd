# shippEdd implement — run the phase unattended, merge per target

You are the orchestrator for the execution half of the phase loop. The phase's plans run one at a time, in plan order, each a detached executor inside the phase's per-target agent worktree; you watch each run to resolution, gate it on the SUMMARY oracle, recover failures within the bound, and merge each target's agent branch when its merge point comes. You never implement anything yourself and never wait idly — the watch script blocks for you. Executors own git inside their worktrees; you own git everywhere else: merge-back and the docs-side commits. Nothing this skill runs writes per-run state into the repo — dispatch state (prompt, log, markers, fork base, attempt ledgers) is transient under `$TMPDIR`, and plan state is derived from artifacts.

**Auto is the default** — a single visit runs the whole phase: dispatch → watch → gate → recover → … → merge → complete, stopping only at completion, budget exhaustion, or a judgment stop. **`/skill:implement manual` is the opt-out**: it stops after each dispatch (the classic re-entry cadence) and asks — in the grilling format — instead of auto-recovering, at every failure. The mode is the skill's first argument; anything other than `manual` is auto.

`<state>` is the workflow state dir resolved in step 0; all other paths are relative to it or to the repo root. This skill is self-contained: its scripts (`scripts/state-dir.sh`, `scripts/dispatch.sh`, `scripts/dispatch-plan.sh`, `scripts/watch-wave.sh`, `scripts/merge-back.sh`) live in this folder; phase templates live in the skill's own `bootstrap/templates/` (sibling of this skill's folder).

## Ground rules

1. **Orchestrate, don't labor** — executors implement in fresh, detached contexts, inside the phase's per-target worktree. Your session sees dispatch lines, resolution lines, and merge lines — never implementation detail; `watch-wave.sh` does the blocking.
2. **Artifacts are truth** — plan `NN-YY` is **executed** iff `<state>/phases/<NN>-<slug>/NN-YY-SUMMARY.md` exists with `status: complete` in its frontmatter, and **landed** iff, in addition, its target's log carries the phase's per-target merge commit `merge(<NN>-<slug>/<target>):`. Transient run state in `$TMPDIR` is advisory (liveness, logs, ledgers); when it is missing — wiped tmp, reboot — derive from artifacts, never treat missing transient state as failure. This skill is idempotent and may be re-run at any moment, mid-plan, mid-phase, or after a crash.
3. **Plan-time data is logical order** — `wave`, `depends_on`, and `target` were precomputed by the planner into each plan's frontmatter (a missing `target` means `master`). You read them as-is and never recompute them; they define the sequential order you execute and the merge points you compute in step 2.
4. **Sequential by law** — one executor at a time. All of a target's plans share that target's agent worktree (forked from the target HEAD when the loop first dispatches into it; branch `agent/<NN>-<slug>/<target>`), so later same-target plans build on earlier ones' commits. `dispatch-plan.sh` refuses a second live executor in a target worktree — never race it, never work around the refusal.
5. **Facts from disk, decisions to the user** — anything readable (summaries, run state, git log, STATE.md) is read, never asked about. Questions — manual mode and genuine blocks only — use exactly this format:

   ```
   ❓ <question>
     ➡️ 1. <recommended answer>
       2. <option>
       3. <option>
   ```

6. **Bounded recovery** — every failed plan and every merge-back halt gets model-driven recovery: diagnose from the artifacts, repair, retry — at most **2 retries / 3 attempts per plan and per merge**, enforced mechanically (`dispatch-plan.sh` and `merge-back.sh` refuse the fourth; `watch-wave.sh` exits 3 at exhaustion). You may stop **earlier** when a retry clearly cannot help (a missing decision, contradictory instructions) — never burn attempts on hopeless retries; never exceed the budget; never auto-skip a plan. On exhaustion or a judgment stop, present the failure dossier (step 5) and stop.
7. **Recommend and stop** — the visit ends at phase completion or when you genuinely cannot proceed; the skill ends by naming the next command (`/skill:review`). Never run it yourself.

`/skill:implement` turns approved plans into finished work — **unattended by default**. ## Common questions

**Why sequential now?**
One executor at a time, all of a target's plans sharing its worktree, was chosen over same-wave parallelism: later same-target plans build directly on earlier ones' commits, merges become one bubble per target, and the loop needs no babysitting between waves. Hybrid parallelism (concurrent plans on different targets) is deferred, not rejected — the `wave`/`depends_on` frontmatter still carries the logical order, so a future phase can re-introduce parallelism without re-planning old phases.

**Who merges, and when?**
The orchestrator gate, never the executor. A target's agent branch merges with `--no-ff` right before the first later plan that consumes it, or when its last plan has executed — validated against the recorded fork base first; drift or conflict halts with a handoff naming the plan, branch, worktree, and SHAs. Docs-side commits (each SUMMARY as it lands; ROADMAP ticks + STATE sync after the merges) land on the planning branch.

**What happens when a plan fails?**
The watcher resolves the failure and hands the facts to the loop; the loop diagnoses (log tail, marker reason, branch state) and, unless a retry is clearly hopeless, writes fix instructions and re-dispatches with `--force` (prior commits are verified and continued, never redone). Three attempts is the hard ceiling — the fourth dispatch is mechanically refused and the loop stops with the dossier. The human then fixes by hand, re-plans, or records the skip.

**What's in the failure dossier?**
The run log's path (with tail), the one-line failure reason, the agent branch's last commits, and the attempt ledger — everything needed to decide without re-deriving context.

**How do I check on a running phase?**
The dispatch line prints the run dir (`${TMPDIR:-/tmp}/shippEdd/<phase>/<plan>/`): `tail` the log there, or run `dispatch.sh --status --state-dir` against it. The loop itself prints a heartbeat while watching.
